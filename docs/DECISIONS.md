# DÉCISIONS

- D1 (validée 2026-10-11) — supabase-js + RLS au lieu de Prisma : Prisma se connecte en rôle privilégié et contourne la RLS exigée.
- D2 (validée 2026-10-11) — Supabase Auth au lieu de NextAuth : imposé par le cahier des charges (mdp + lien magique).
- D3 (validée 2026-10-11, caduque depuis D25) — Mode invité stocké en IndexedDB, pas localStorage (interdit par le modèle).
- D4 (validée 2026-10-11) — Charte VINCI et patterns UI du modèle Conduc Rail conservés ; polices VINCI fournies le 2026-10-11.
- D5 — Lecture d'abaque entre nœuds : valeur la plus défavorable par défaut ; interpolation seulement si autorisée par la doc ; jamais d'extrapolation.
- D6 — Tout abaque importé arrive en `a_verifier` ; passage en `verifie` uniquement après contrôle humain contre le PDF constructeur.
- D7 — PDF généré côté client (@react-pdf/renderer) pour fonctionner en mode invité (motif caduc depuis D25 ; génération client conservée).
- D8 — Moteur de calcul dans `src/engine/`, pur TypeScript, testé Vitest.
- D9 — Polices VINCI commitées dans le dépôt public (choix explicite de l'utilisateur, 2026-10-11) ; Expanded, Rounded et Dingbats non utilisées.
- D10 — `load_chart_points.y` NOT NULL DEFAULT 0 : colonne de clé primaire (PK(chart_id,x,y)) ; pour `axis_y = 'none'`, y = 0 imposé par trigger.
- D11 — `study_versions` immuable : aucun droit UPDATE/DELETE pour `authenticated` + trigger refusant tout UPDATE (même `service_role`) ; suppression uniquement par cascade de l'étude.
- D12 — `lifting_studies.current_version_id` : FK composite (id, current_version_id) → study_versions(study_id, id) pour garantir que la version courante appartient à l'étude.
- D13 — `chart_sources.owner_id` ajouté (NULL = source publique) pour permettre aux utilisateurs de sourcer leurs abaques perso ; lecture si propre ou référencée par un abaque visible.
- D14 — `machine_types` et `manufacturers` : référentiels en lecture seule hors `service_role`.
- D15 — Passage d'un abaque perso en `verifie` : `verified_by`/`verified_at` forcés par trigger à l'utilisateur courant ; un abaque public n'est modifiable que par `service_role`.
- D16 — Fonctions utilitaires/triggers dans un schéma `private` non exposé, `search_path = ''` ; seuils verdict contraints 0 < vert < orange ≤ 100.
- D17 — Moteur : domaine de lecture d'une ligne d'abaque = [x min ; x max] de CETTE ligne ; y intermédiaire ⇒ les deux lignes encadrantes doivent couvrir la portée, sinon hors abaque ; cellule `capacityKg: null` touchée ⇒ hors abaque.
- D18 — Moteur : bornes des zones (tolérance 1e-9) vert si taux < seuil vert, orange si seuil vert ≤ taux ≤ seuil orange (80 % et 100 % exacts = orange), rouge au-delà ; taux > 100 % toujours bloquant ; seuils valides si 0 < vert ≤ orange ≤ 1.
- D19 — Moteur : élingage 3 ou 4 brins ⇒ 2 brins porteurs sauf palonnier/équilibrage déclaré ; β ≤ 45° conforme, 45° < β ≤ 60° réserve, β > 60° bloquant.
- D20 (facteur de mode retiré par D32) — Moteur : aucun facteur de mode normatif codé ; CMU utile = CMU direct × facteur de mode saisi, comparée à l'effort par brin (sollicitation « brin ») ou à la masse suspendue totale (sollicitation « ensemble » : palonnier, crochet, élingue multibrins dont la CMU par mode inclut l'angle).
- D21 — Moteur : portance du sol, limites de vent et distance minimale aux lignes électriques sont des entrées sans valeur par défaut (absentes ⇒ bloquant « donnée manquante ») ; égalité au seuil acceptée.
- D22 — Moteur : vent en m/s en interne (helper km/h → m/s) ; masses en kg, efforts en kN (g = 9,81) ; aucun arrondi interne, formules symboliques.
- D23 — Moteur : champ `flechetteReplieeKg` sans accent (identifiant ASCII) ; contrôles renvoient `Check<T>` = `Calc<T>` + `issues[]` (bloquant/réserve) agrégés par `computeVerdict`.
- D24 — Abaques : saisie dans data/charts/<machine>/ (machine.json + un CSV par configuration), validation `npm run charts:check`, import par `npm run charts:sql` → supabase/seed/charts.sql ; cellules vides non stockées (nœud absent = hors abaque) ; slug de configuration dans params.slug.
- D25 (demande utilisateur 2026-10-11) — Suppression du mode invité ; accès sur compte validé par l'administrateur. `profiles.statut` (`en_attente` par défaut / `approuve` / `refuse` / `suspendu`), `est_admin`, `statut_modifie_par/le` ; profils existants à la migration passés en `approuve`. Policies RESTRICTIVES `private.est_approuve()` sur toutes les tables de données + buckets `user-files` / `chart-sources` (désormais privé) ; plus aucun droit `anon`. Garde par trigger (`current_user` = `authenticated` ⇒ statut intouchable). Admin via RPC SECURITY DEFINER `admin_lister_comptes` / `admin_definir_statut` (refus hors admin, sur soi-même ou sur un autre admin, retour à `en_attente` interdit) ; premier admin par `private.designer_admin(email)` (postgres / service_role). Brouillon IndexedDB, reprise de brouillon, catalogue statique de repli et mention PDF « Document non enregistré » supprimés ; `/outil` crée l'étude dans un projet. Redirections `suivant` filtrées par `cheminInterne` (chemin interne uniquement).
- D26 — Notification e-mail de l'administrateur à chaque inscription : trigger `profiles_notifier_inscription` (pg_net) → Edge Function `notifier-inscription` (Resend), URL et secret partagé lus dans Vault ; sans secrets Vault, aucun appel ; sans `RESEND_API_KEY`, la fonction journalise et répond 200. Le bouton « Valider la demande » mène à `/admin/comptes/<id>` : aucune décision sur simple ouverture (GET), uniquement au clic (Server Action).
- D27 — Connexion par lien magique retirée de l'interface (2026-10-11, demande utilisateur) : connexion par e-mail + mot de passe uniquement. Un appel direct à l'API OTP ne donnerait qu'un compte `en_attente`, sans accès.
- D28 — Notification d'inscription envoyée via Resend en mode test (expéditeur onboarding@resend.dev, destinataire = adresse du compte Resend) ; domaine vérifié reporté (choix utilisateur, 2026-10-11).
- D29 (décision utilisateur 2026-10-11 : « On part du principe que les abaques sont bons. ») — Remplace D6 pour l'effet sur le verdict (D6 reste valable pour le statut d'import `a_verifier` → `verifie`). Le statut d'abaque n'ajoute plus de réserve (réserve `ABAQUE_A_VERIFIER` et avertissement de lecture supprimés du moteur) et n'est plus signalé en alerte dans le parcours d'étude ; il reste affiché (badge, source) dans le catalogue `/machines` et la fiche machine, et comme information de source à l'étape Machine. PDF : encadrés « ABAQUE À VÉRIFIER » remplacés par un paragraphe sobre en synthèse (abaque utilisé, source, vérification contre la machine réellement présente et sa doc constructeur à jour) ; mention permanente inchangée. Versions stockées (immuables, D11) : `verdictDepuisResultat` affiche ADEQUAT quand la seule réserve stockée est `ABAQUE_A_VERIFIER` (sans bloquant).
- D30 (demande utilisateur 2026-10-11) — Projets d'exemple à la validation du compte : 2 projets « [EXEMPLE] » (Lyon : 2 études GMK3060L ; Montpellier : 1 étude Cat 323) créés une seule fois quand `profiles.statut` passe à `approuve` (trigger `profiles_exemples_validation`, couvre `admin_definir_statut` et `designer_admin`), sans protection (modifiables / supprimables). Modèles dans `private.modeles_exemples` (migration générée par `npm run exemples:sql` depuis `scripts/exemples/`, data/result = moteur actuel, marqueurs `@@…@@` pour les identifiants du catalogue et le rédacteur) ; un `result` par statut d'abaque car le texte de source du moteur contient « statut : à vérifier / vérifié » (le verdict n'en dépend pas, D29). `private.creer_exemples(uuid)` (SECURITY DEFINER, non exécutable par anon/authenticated) : suivi `private.exemples_servis`, résolution par `machines.model` + `params.slug` (catalogue public), empreinte md5 de l'abaque comparée à celle des modèles ⇒ projet sauté (notice) si absent ou modifié ; toute erreur capturée, la validation n'échoue jamais. Comptes déjà approuvés lors de la migration marqués servis (rien n'est créé, l'administrateur a déjà ses exemples).
- D31 (2026-10-12) — Confirmation d'adresse e-mail à l'inscription désactivée dans Supabase Auth : le service d'e-mail intégré de Supabase limite l'envoi à quelques messages par heure (erreur `over_email_send_rate_limit` constatée sur plusieurs inscriptions) et Resend en mode test (D28) ne peut écrire qu'à l'adresse du compte. La validation par l'administrateur (D25) reste le seul contrôle d'accès : il vérifie l'identité du demandeur avant d'accepter. `inscription` gère déjà la session immédiate (redirection `/compte-en-attente`). Message dédié si la limite d'envoi est encore atteinte.
- D32 (demande utilisateur 2026-10-12) — Facteur de mode supprimé : chaque accessoire porte une seule CMU, lue sur l'étiquette pour le mode d'élingage utilisé (`cmuKg`), comparée à l'effort par brin ou à la masse de l'ensemble (D20 modifiée). Sauvegardes antérieures converties au chargement (`fusionnerAvecDefauts`) : CMU = CMU direct × facteur de mode (CMU direct seule si le facteur manquait). Coefficient de marge sur la masse de la charge (`charge.coefMarge`, défaut 1, saisi entre 1 et 3) : majore la charge dans la charge totale et dans la masse sous crochet (élingage) ; formule et valeur brute affichées.
- D33 (demande utilisateur 2026-10-12) — Seuil vert par défaut 90 % (au lieu de 80 %) : moteur, études neuves, `user_settings.threshold_green` (défaut 90 ; réglages restés à 80 / 100 passés à 90 / 100 par migration). Études et versions déjà enregistrées inchangées (D11).
- D34 (demande utilisateur 2026-10-12) — Étape Sol : portance minimale requise q_min = F / S calculée en direct (moteur `minBearingCapacity`, affichage kPa / bar / t/m², sans coefficient de sécurité) dès que l'effort et la surface d'appui sont saisis ; le contrôle contre la portance admissible saisie est inchangé.
- D35 (demande utilisateur 2026-10-12) — Page Machines : liste compacte (recherche, filtres type / constructeur, groupes repliables) et onglet « Disponibilité des abaques ». Machines sans abaque tenues dans `data/machines-sans-abaque.json` (à garder cohérent avec docs/ABAQUES.md) ; classeur `docs/Machines-abaques.xlsx` régénéré par `npm run machines:xlsx`.
- D36 (demande utilisateur 2026-10-12) — PDF source des abaques du catalogue : bucket privé `chart-sources` (lecture comptes approuvés, écriture service_role), nom du PDF d'origine à la racine du bucket (déposé par l'utilisateur le 2026-10-12, contrôlé à l'octet près ; null pour Cat 323, GMK3060L et LTM 1060-3.1, documents en ligne) déclaré dans `source.file_path` de data/charts/<slug>/machine.json et reporté dans `chart_sources.file_path` par `npm run charts:sql`. Fichiers déposés hors dépôt (dépôt public ; tableau de bord Supabase → Storage). Liens par URL signée (1 h) : ligne de la liste Machines (« PDF »), fiche machine (« Voir le PDF de l'abaque » / « Télécharger »), étape Machine de l'assistant (lien vers la fiche). Fichier absent ⇒ aucun lien.
- D37 (demande utilisateur 2026-10-12) — Page d'accueil `/` après connexion (défaut de `cheminInterne`) : logo, raccourcis (nouvelle adéquation, projets, catalogue, disponibilité des abaques), 3 projets récents, présentation PDF intégrée (`public/documents/presentation-adequation-levage.pdf`, derrière le middleware : connexion exigée). Entrée « Accueil » en tête de la barre latérale.

Catégories TE et seuils du Code de la route sourcés dans docs/TRANSPORT.md ; accompagnement selon la lecture la plus prudente de l'art. 13 (version 2024 non lue) ; véhicules à caractéristiques indicatives.
